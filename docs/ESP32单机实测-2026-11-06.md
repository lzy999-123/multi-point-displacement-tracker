- esptool 识别：ESP32-S3 QFN56 rev v0.2，8MB PSRAM，8MB Flash。
- UDP 发现设备编号 1，当前视频地址 `http://192.168.110.43:81/stream`。IP 由 DHCP 分配，后续可能变化。
- 初始固件返回 HTTP 200 和 MJPEG 头，但约 25.3 秒内 128 个载荷均无法解码。
- 读出 Flash 后核对：应用区域与 `D:/esp32/build-out/variant/out/displacement_cam.ino.bin` 逐字节一致。
  对应测试源码跳过摄像头初始化，发送带 JPEG 首尾标记的 5000 字节随机数据。初始“有 HTTP 响应”不能证明摄像头工作。

用户明确授权后，先完成 8MB 整片读取，再执行 `verify-flash`，芯片端 digest 校验成功。

使用 arduino-cli 编译，通过 COM5 / 230400 烧录并完成写入哈希校验。

- 应用 BIN：`D:/esp32/build-out/device-check-20261106/displacement_cam.ino.bin`

## 网络与发送缓冲对照

- 推流后的相机 ping：30 次收到 22 次，丢包 26%，已收到响应的 RTT 为 85～398ms，平均 247ms。
- 空闲相机 ping：15 次收到 14 次，丢包 6%，RTT 为 32～221ms，平均 104ms。
- 同期电脑到路由器：15 次全部收到，RTT 为 1～4ms，平均 1ms。

这些结果和板端每帧发送耗时数秒的日志表明瓶颈集中在 ESP32 发送及其网络路径，
不能据此单独认定是供电、射频干扰、路由器或某一驱动缺陷。

临时对照仅将发送副本从 PSRAM 改为内部 RAM，项目源码未修改。
约 24.5 秒收到 10 张有效图像，随后读超时；仍有长时间无帧，没有达到稳定改善标准。
该变体不作为正式交付，完成对照后恢复上述正式固件。

恢复正式固件后再次校验写入哈希成功，启动仍识别 GC2145。最后一次取流连接在约27.7秒后超时，
未取得完整图像；同一观察窗口串口记录采集约15.0fps且无重启。此结果进一步说明真实图像虽已获取过，
连续可用性仍不合格。设备最终保留正式固件，没有保留内部 RAM 实验变体。
