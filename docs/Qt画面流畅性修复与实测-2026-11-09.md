# Qt 视频显示修复与实机验收

日期：2026-11-09。设备：一块真实 ESP32-D0WD-V3 + 4MB PSRAM + OV3660，USB-SERIAL CH340 / COM5。

## 当前可使用的结果

双击 `host/run.cmd`，或运行更新后的 Qt Creator Release 程序。程序自动打开本机配置的COM5、
连接已保存的相机热点 `disp-cam-1`，以 `udp://192.168.4.1:5006` 显示通道1。
关闭后释放串口并恢复启动前的WiFi，没有保活后台进程。首次画面约3.6秒。

当前固件为纯AP、信道1、20MHz带宽、320×240、硬件JPEG质量20；直连期间电脑WiFi不接实验室路由器。
这是单路相机交付，三路并发、控制转发、云台闭环和位移测量精度没有在本轮验收。

## 公用网络重测

用户将实验室 `DH4504` 从Private切回Public后，读取Windows配置确认已是Public，再烧录STA模式重测。
10秒源帧验收收到0张完整图像，随后20秒Qt真实显示也是0帧；串口仍有 `errno=12`。
因此本次没有把网络类别切换当作修复，也没有关闭系统防火墙或修改Clash。

STA旧配置、禁用11n对照和调整有限重试均未让实验室链路达标。转为相机AP后，发送失败消失，
信道1与WLAN流媒体提示、暂时禁用背景扫描组合下完成上述验收。由于同时改变了链路条件，
不能将收益精确归因于单一参数，更不能断言实验室路由器的具体硬件故障。

证据：`public-sta-decoded-10s/result.json`、`public-sta-qt-20s.json`、`serial-public-sta.log`。
实验室模式仍需独立解决后才能恢复三路共享路由器组网。

## 修复内容与软件验证

- Qt UDP：验证对端地址和端口，完整校验分片边界与同帧元数据；处理乱序、重复及16位序号回绕。
- 断流1.5秒后重建序号基准，恢复相机重启归零后的画面；损坏JPEG不推进已交付序号。
- 每批只解码最新完整帧，避免积压旧图像。
- 正式程序限制单实例，避免多个客户端相互覆盖相机推流目标。
- 本机CH340串口随窗口生命周期管理；WLAN通过Native WiFi API连接相机，退出时恢复原网络和扫描设置。
- 固件：发送失败有限重试；超过预算或缺片则回收旧帧；修正调试日志截断长度和资源创建失败处理。
- UDP验收工具：实际解码、逐帧验证320×240、拒绝重复序号、纳入首尾静默间隔、失败返回非零退出码。
- 显示验收：窗口置顶，去掉测试期间的PNG截图编码，结束后才保存截图，保留原始事件。

Qt核心回归：**20 passed、0 failed、0 skipped**，包含实际HTTP模拟相机和4项UDP网络测试。
Python VID1测试6项通过，已有源帧指标测试7项通过。
无效JPEG、160×120和无视频三个回环反例现均不通过，退出码1。
