# GitHub 参考项目调研（2026-11-06）

目的：为本项目 ESP32-S3 + GC2145、320×240、Windows Qt、DH4504 路由器下的实时视频寻找可复用实现。
已通过 GitHub API 读取项目说明、关键源码及依赖；他人报告的帧率与本机实测分开记录。
本次调研没有执行下载仓库里的脚本，也没有直接烧录第三方预编译镜像。

## 重点参考

### 1. Espressif esp_new_jpeg：编码器首选

- [官方库与性能说明](https://github.com/espressif/esp-adf-libs/tree/master/esp_new_jpeg)
- [官方 README](https://github.com/espressif/esp-adf-libs/blob/master/esp_new_jpeg/README.md)
- 调研树：`84a8c3d477e5959b3392c65126e41ed0dcedea27`。

支持 ESP32-S3、RGB565/YUV422 等输入和 4:2:0 输出。官方 S3 软件编码基准中，QVGA YCbYCr 输入约45.3fps，
这是单独编码能力，不包括相机取帧、WiFi、接收解码和界面绘制，不能当作本系统帧率。

本机工具链已自带该库，不需要先引入新的外部依赖。实机对照中，RGB565 输入压缩约29.5ms，
YUV422 输入压缩约16.1ms；旧 `frame2jpg` 路径约65ms。但网络仍有停顿，压缩加速本身没有完成系统验收。
S3 在此使用的是软件 JPEG，不能误称硬件编码器；部分第三方 README 对这一点的描述不准确。

采用方向：对齐输入缓冲、复用编码句柄与输出缓冲、明确 YUV 字节顺序，保留采集和网络独立任务。

### 2. arms22/esp32_camera_udp_streaming：普通 WiFi UDP 参考

- [项目](https://github.com/arms22/esp32_camera_udp_streaming)
- [发送端](https://github.com/arms22/esp32_camera_udp_streaming/blob/main/esp32_sender/main/camera.c)
- [Python/OpenCV 接收端](https://github.com/arms22/esp32_camera_udp_streaming/blob/main/python_receiver/receiver.py)
- 调研树：`35c56f48b70ce4d1f1537ccae16dd7cbe92c758f`。

项目使用 OV2640、修改过的相机接收路径、ESP-IDF 4.2；作者展示的高帧率不能套到 GC2145。
发送和接收思路值得参考：按 UDP 到达数据组帧、接收端及时消费最新图像，而不是积压旧帧。
原接收端依赖 JPEG 首尾标记；本项目若采用，需要自行增加会话、帧号、分片号、长度边界、过期丢帧和必要冗余，
并保持现有三路 Channel 接口。UDP 也不能保证在任意严重丢包网络下无卡顿。

仓库根级许可证信息未识别到；`main.c` 有 CC0/Public Domain 声明，但不能据此假定仓库所有文件都同样授权。
本次只参考架构，不整仓复制。

### 3. Ashley-QwQ/yahboom-esp32s3-gc2145-hires：同传感器的实物与时钟依据

- [项目](https://github.com/Ashley-QwQ/yahboom-esp32s3-gc2145-hires)
- [相机配置](https://github.com/Ashley-QwQ/yahboom-esp32s3-gc2145-hires/blob/main/firmware/yahboom_gc2145/config.h)
- [实际取帧与 HTTP 实现](https://github.com/Ashley-QwQ/yahboom-esp32s3-gc2145-hires/blob/main/firmware/yahboom_gc2145/yahboom_gc2145.ino)
- 调研树：`6cdc9e0fb9fbeeba4e5cb6f8c32bd3c988ba7733`；Apache-2.0。

使用 S3 + GC2145、YUV422、单缓冲；为其 2MB PSRAM / 4MB Flash 板提供高分辨率静态抓图与控制。
作者明确没有连续 MJPEG：XGA 抓图约1.2秒，不是流畅视频项目。其10MHz时钟和寄存器控制方法可作为对照依据。

其 DVP 数据引脚顺序与本项目现有 S3-EYE 配置不同，且 PSRAM 类型/容量不同，不能直接烧录或照搬引脚表。
是否更换时钟必须对本板实测；高分辨率抓图通过不能证明低延迟流媒体通过。

### 4. jeanlemotan/esp32-cam-fpv：低延迟与纠错架构参考

- [项目](https://github.com/jeanlemotan/esp32-cam-fpv)
- [发送和 FEC 调度](https://github.com/jeanlemotan/esp32-cam-fpv/blob/main/air_firmware/main/main.cpp)
- 调研树：`adc1e5c040bada4780de0db60716af411d326435`；MIT。

OV2640 JPEG、相机 DMA 分段、FEC 冗余、1400字节数据包，具有作者报告的高帧率/低延迟结果。
但它使用 WiFi 原始帧注入、树莓派和支持监听模式的特定 USB 网卡，不是经普通路由器传输的 Windows 方案。
可参考序号、冗余和有界队列，不能把作者的20～50ms延迟当作本项目预期或验收结果。

## 次要参考与排除原因

- [espressif/esp32-camera](https://github.com/espressif/esp32-camera)：官方 GC2145 驱动和缓冲使用说明。
  RGB/YUV 连续双缓冲有资源压力；但本机将旧 RGB 编码路径改单缓冲后采集仅约8.5fps且网络未改善，
  说明必须结合编码器和取帧路径整体实测，不能只按一条配置建议推断完成优化。
- [Camemake/GC2145_ESP32_DVP_DRIVER](https://github.com/Camemake/GC2145_ESP32_DVP_DRIVER)：可查传感器接入思路。
  关键包装源码仅865字节，使用的 `pin_sda/pin_scl` 等字段也需与实际驱动版本核对，没有读到可证明本项目稳定推流的实现。
  暂不替换已能初始化的官方驱动。
- [KisalRojitha/esp32cam-gc2145](https://github.com/KisalRojitha/esp32cam-gc2145)：针对普通 ESP32 + GC2145，
  说明中原始 RGB TCP 传输在拥挤网络上反而慢，与本机网络瓶颈相符。它的部分 S3/5GHz 描述不准确，不能直接照搬。
- [chayuto/ws-ESP32-S3-CAM](https://github.com/chayuto/ws-ESP32-S3-CAM)：同系列硬件资料较完整，但当前主要项目是音频监测，
  没有把它视为已验证的 GC2145 流畅视频参考。

## 本项目下一步

优先复用官方软件编码器，保持320×240和有界帧缓冲；在原 DH4504 网络上验证带序号与冗余的 UDP 最新帧传输。
只有实机逐秒帧数、最大无帧时间、解码错误、重启，以及实际 Qt 绘制结果达到标准后，才切换默认链路。
网络传输、固件代码、上位机显示三者分开验收。当前仍未达到用户要求的“稳定运行、无卡顿”。

调研后的实板 UDP 原型也未达标：40秒仅6帧、首帧约31.6秒；不能把协议换成 UDP 直接宣称修复。
该原型不作为默认链路。正式项目先保留已经出现过连续60秒879帧的 QVGA/JPEG质量40、TCP合并小包和发送超时方案，
但该60秒窗口最低仍有6fps，最长无帧约348ms，因此也未达到每秒至少10帧的验收标准。

另检索到官方仓库中关于 S3 持续上行期间歇性停发的[问题报告 #18683](https://github.com/espressif/esp-idf/issues/18683)。
报告配置与本机并不完全一致，当前没有证据认定它就是本项目根因，不能据此直接宣布某个 SDK 版本能修复。

恢复正式项目固件后的实际Qt窗口120秒复测也未通过：收到331帧、绘制331帧、最大停帧约34.7秒。
当前相机和上位机已能真实取图/绘图，稳定传输目标仍未完成，见 [优化记录](ESP32推流优化-2026-11-06.md)。

原始 GitHub API 元数据和调研源码保存在 `tmp/esp32-optimize-20261106/github-research/`，不纳入项目发布内容。
