# ESP32-S3 更换 OV3660 实测

日期：2026-11-11。用户已将原GC2145替换为OV3660，目标仍是通过实验室WiFi稳定显示。通道1保留ESP32-CAM，S3仍为通道2。本次仅发现COM6，COM5未连接；没有将单路结果表述为双路通过。

## 已确认

- COM6启动读到传感器PID `0x3660`，自动进入硬件JPEG；实验室SSID为DH4504，IP为`192.168.110.59`。
- 原S3固件已有OV3660识别分支，首次测量未改写固件；恢复版本应用SHA256为`4f3211dfd178101e6465665cbe35efa7199df6e39bce5fb9bc5febfd10286f1e`。
- 320×240实际JPEG已解码并保存。板端日志约27fps，硬件JPEG后的复制/处理统计约1.0～1.3ms/帧；不能把日志中“压缩”标签理解为传感器JPEG编码耗时。它不包含完整曝光采集和无线发送时延。
- 没有受控的同场景、同曝光GC2145/OV3660画质对照；当前结果不能证明画质提升程度。

尝试电脑接已保存的实验室5GHz、S3保持2.4GHz时，Windows明确返回该5GHz网络当前不可用。因此没有执行跨频段视频测试，电脑连接确认恢复DH4504。

## 当前配置与证据

上位机项目及部署目录的第二路URL已同步为`http://192.168.110.59:81/stream?nodelay=1`。第一路URL及COM5映射保留。该选项是可继续对照的设置，尚非通过长期验收的修复。

恢复原固件后，通过串口`h`请求20MHz带宽，API返回0，状态报告bandwidth=1；随后复位原固件的默认状态也为bandwidth=1。因此这不是确认改变了带宽的独立对照。该30秒窗口收到81帧、最大无新帧14502.39ms，未通过，原始结果在`s3-ov3660-ht20-source/`。复位后没有保留额外的无线参数改动。

用户明确说明S3直插电脑、没有外部扩展坞；Windows显示通用USB集线器不能证明有外接扩展坞。随后设备重新枚举，USB路径由`1-5.1`变为`1-1`，串口从COM6变为COM3；已通过ROM `esp32s3`、设备编号2、PID=0x3660硬件JPEG和`.59`地址重新确认身份。上位机项目/部署配置的第二路串口已同步COM3。物理供电电压没有测量，不能由此认定供电已改善或是故障根因。

COM3上的60秒连续源流复核：全程一次HTTP连接、无读超时、无解码失败、无序号重复或乱序；时间窗内1335帧，另有一帧在60秒截止后到达，总接收计数1336。最长无新帧1643.96ms、最低逐秒0帧，验收仍未通过。采集日志约27fps，网络发送仍有约1573ms单帧长耗时；没有用全程平均帧率替代逐秒和最长停顿门槛。记录在`s3-ov3660-com3-source60/`。

随后同配置完成90秒Qt正式第二路实际显示，2172次新绘制、320×240、没有重连；预热后最长无新绘制1687ms，最低逐秒0帧，严格验收仍未通过。原始计数、状态和截图在`s3-ov3660-com3-qt90.json`及相邻文件。与此前窗口相比观察到停顿减少，但测试场景、时段和USB路径未形成可重复的单变量试验，不能断言改善由USB路径引起。

最终保留原S3固件、20MHz XCLK、OV3660硬件JPEG、COM3/第二路、DH4504及nodelay=1；8MHz候选已移除。结论是换装兼容性和实验室真实传图均已验证，持续流畅目标未通过。当前精确状态见`s3-ov3660-retained-state.json`与`current-status.json`。

原始证据位于`output/实验室网络实测-20261111/`下的`s3-ov3660-initial/`、`s3-ov3660-nodelay1-source/`、`s3-ov3660-nodelay1-qt130.json`及串口/截图、`s3-ov3660-8mhz/`、`s3-ov3660-clock-comparison/`和`s3-ov3660-pc5ghz/`。
