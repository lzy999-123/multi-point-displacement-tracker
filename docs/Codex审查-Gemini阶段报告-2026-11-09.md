## 结论

固件的 8KB 视频任务栈、静态分片缓冲、每帧调度延时和有限发送重试均已实际落地，具有合理工程依据。但报告混合了真实代码改动、历史测试、待验证假设和尚未实现的架构，不能作为“硬件已完全稳定，准备进入三路闭环联调”的验收依据。

最优先处理的是验收脚本误判和 Qt 相机重启恢复问题。当前只能表述为：单相机视频链路调试中；有历史 UDP 接收性能记录，当前版本的真实解码、Qt 显示、长期运行及三路并发仍待重新验收。

本次没有修改生产源码、切换网络、关闭代理、变更防火墙、打开设备串口或烧录固件。新增审查文档和 `tmp/codex-review-20261109/` 回环复现程序，重新构建测试目标并在单独的 `host/build/codex-review-runtime/` 中运行。回环测试使用模拟报文，不构成实机性能证据。

## 一、已复现的问题（按处理优先级）

### P1：UDP 验收脚本能把无效视频判为通过

位置：`tools/check_esp32_udp_stream.py:120`、`:127`、`:165`。

- 序号比较允许差值为 0，相同序号完整帧重复到达仍可重复计数。
- 所谓 `decode_errors` 只检查 JPEG 的 SOI/EOI 标记，并未执行实际解码。
- 没有核验输出图像宽高，因此不能证明 320×240。
- `max_gap_ms` 只计算预热后相邻收帧间隔，遗漏预热边界到首帧和末帧到测试结束的静默时间。
- 入口没有依据 `passed` 返回非零退出码，未通过的测试也会让调用方得到成功退出码。

本机直接运行原验收脚本，回环发包复现如下：

| 输入 | 原脚本结果 | 实际含义 |
| --- | --- | --- |
| 同一序号 7，循环发送首尾带 JPEG 标记的无效字节串 | 91 帧、22.72fps、`decode_errors=0`、`passed=true` | OpenCV 无法解码；也没有产生 91 个不同源帧 |
| 连续递增序号，真实 160×120 JPEG | 89 帧、`passed=true` | 分辨率不满足 320×240 |
| 4 秒内完全无帧 | `passed=false`，进程退出码仍为 0 | 自动化调用不能依据退出码识别验收失败 |

证据：`tmp/codex-review-20261109/checker-probes.json`；复现入口：`checker_review.py`。这些数字是人为构造的回环测试，不能与摄像头实测混用。

建议：严格拒绝重复序号；实际解码并校验每帧分辨率；保留原始序号、收包/解码时间及丢帧统计；纳入测试边界的静默间隔；失败返回非零。随后使用实际 Qt 解码和绘制路径验收。

### P1：Qt UDP 接收器不能及时恢复相机重启后的序号归零

位置：`host/udpstream.cpp:99`、`:152`。

接收器保留 `m_lastDeliveredSeq`，超时处理只改变状态并再次发 VREQ，没有重新建立序号基准。相机重启会把 `currentSeq` 置零，但后续完整帧仍可能被当成旧帧丢弃。

直接编译当前生产 `UdpStream`，发送有效 320×240 JPEG：先发送序号 300、301，模拟相机重启后发送 0～19。结果为重启前解码 2 帧，重启后发送的 20 帧全部未交付。该断流的持续时间取决于此前序号，可能显著超过 3.5 秒看门狗周期。

建议：在确认断流后清空组帧和序号基准，或协议增加启动会话标识。用“重启前后连续视频”测试验证恢复时间，并兼顾正常乱序和 16 位回绕。

证据：`tmp/codex-review-20261109/qt-udp-probes.json`；复现入口：`udp_review.cpp`。

### P2：Qt 接收器没有核验报文来源和同帧头部一致性

位置：`host/udpstream.cpp:107`、`:125`、`:139`。

当前仅验证 VID1 魔数和部分长度，没有过滤发送方地址、端口或设备编号。本机在配置的服务器之外，使用另一个 UDP socket 向接收端发送有效报文，成功交付 1 帧，证明来源过滤缺失。

另外，同一序号的后续分片没有确认 `chunk_count`、`frame_size` 与已建立的槽位一致；`chunk_index` 只和新包的 `chunk_count` 比较，然后直接索引旧槽位的 `chunksReceived`。不一致报文有越界访问风险；本次未对越界路径做运行复现。

建议：验证预期对端和设备；完整验证分片数量、长度及元数据一致性；拒绝错误报文后保持已有槽位安全。

### P2：当前 Qt 回归没有保持通过

重新构建 `host/tests/core_test.pro` 后运行：**14 passed、1 failed、1 skipped**。

失败项 `discoveryParsesAnnounce`：`host/devicediscovery.h:26` 已改成优先 UDP，但 `host/tests/core_test.cpp:217` 仍要求 HTTP。应按最终传输策略同步测试和文档，不能继续引用旧的“15 passed”。现有核心测试也没有覆盖新增 UDP 组帧与重启恢复行为。

证据：`tmp/codex-review-20261109/core-test.txt`。

## 二、报告的状态和架构偏差

### Luckfox 架构没有对应当前实现

仓库的 `README.md`、`docs/系统设计方案.md` 和 `stm32/VALIDATION.md` 指向：Qt → WiFi → ESP32-CAM → UART → STM32 → 三组二维 PWM 云台。

`host/channel.cpp:115` 下发控制仍是待实现注释；当前固件没有实现 UDP 5005 控制接收和串口转发。报告中的 Luckfox 接收偏差并直接 PWM 闭环，没有在本工作区找到对应实现。若确实要改用 Luckfox，应先明确其职责以及是否替换 STM32，更新接口和阶段计划。

色块检测使用轮廓矩得到浮点质心，但控制偏移又取整为像素值；没有找到已完成的物理位移标定和精度验收依据。因此“亚像素位移跟踪算法已完成”也超出了现有证据。

### 历史通过记录不能代表当前固件和路由器模式

`tmp/udp-test-20261109/result.json` 确实保留了 30 秒、832 帧、27.7fps、逐秒最低 26fps 的记录。对应文档描述的是 `192.168.4.1` 独立 AP 直连测试；当前配置 `CAM_WIFI_MODE_AP=0` 为路由器 STA 模式。记录文件没有固件哈希、原始帧事件、真实解码及 Qt 绘制指标。

当前固件构建清单时间为 `2026-11-09T21:11:16+08:00`，晚于该 18:52 左右的测试记录。清单中三份源码 SHA256 均与当前工作区一致，应用 SHA256 为 `D720FC2E23ADF8E22105C1207A06581BD31B842337926437348035120AA2851F`。这证明本地构建来源对应当前源码，不能证明板上运行的版本或该版本已经硬件验收。

历史真实 Qt HTTP 显示测试为 724 帧、逐秒最低 7fps、最大间隔 740ms，`passed=false`；不能用不同链路、不同统计口径的 UDP 接收结果直接替代它。

## 三、需要修正的根因解释

| 报告判断 | 审查意见 |
| --- | --- |
| 8KB 栈、静态缓冲彻底根治崩溃 | 改动已存在且方向合理，但本轮未取得对应崩溃回溯、栈高水位和当前固件长跑记录；不能验证精确的“lwIP 消耗超过 2.5KB”及“彻底根治” |
| 每帧延时解决 IDLE1 饥饿 | 当前 SDK `CONFIG_FREERTOS_HZ=1000`，1ms 确实转换成一个 tick；方向合理，长期效果仍需实测 |
| ENOMEM 就是 BA 窗口 6 溢出 | 官方文档支持下层发送缓冲不足引起 UDP ENOMEM；不足以锁定具体 BA 窗口或描述符路径。本地配置同时有动态 TX 缓冲数量 32，不能把它与 BA 窗口 6 等同 |
| 2ms 间隔从数学上保证队列深度为 1 | WiFi 竞争、重传和 AP 调度会改变实际发送完成时间；固定间隔有缓解作用，不能保证无拥塞 |
| SO_SNDBUF 因没有 TCP ACK 释放机制导致 UDP 假性耗尽 | 本地 lwIP `sockets.h:220` 明确把 SO_SNDBUF 标成未实现。移除无效选项合理，但原报告的 ACK/耗尽解释不成立 |
| 必须移除 sendto 失败后的 break | 短延时有限重试合理；重试耗尽后，缺少一个分片的帧已不能完整解码。此时停止该帧并转向新帧，是合理的低延迟策略；继续发送剩余分片不能补回缺片 |
| PWDN 脉冲等于彻底断电、放电、冷复位 | PWDN 是 power-down 控制线，与 RESET 和供电轨不同。驱动本身也有 PWDN 操作；未测量供电轨，不能宣称电源切断或已证明悬空是根因 |
| WiFi 先启动已消除欠压 | 只是改变初始化顺序，没有电压波形或欠压对照证据；而且当前代码在联网前已将 PWDN 拉低，不能理解为整个联网阶段传感器都处于掉电状态 |
| allow-lan:false 导致 gVisor 丢弃所有局域网视频 | 官方含义是是否允许其他设备访问 Mihomo 代理端口，不能直接推导为所有本机 LAN UDP 都被禁。TUN 是否干扰应通过实际路由、抓包和开关对照定位 |
| 改成 Private 即解决入站拦截 | 本轮读取确认 WLAN 为 Private，防火墙仍启用；网络类别不等于对应程序或 UDP 端口已经放行 |
| CH340 关闭串口必然持续拉低 EN | 需要具体底板自动下载电路、驱动行为和 EN 波形证据；不能推广为 CH340 通则。串口开关可能改变 RTS/DTR，但不证明一定持续复位。本轮未发现 COM5，未作实机验证 |

## 四、建议的下一步验收顺序

1. 先修正验收脚本和 Qt 的重启恢复、来源校验，同步 UDP 优先策略对应的测试。
2. 锁定单块板的源码、构建、烧录版本及路由器 STA 模式，保留串口日志和逐帧事件。先做至少数分钟的连续测试，记录重启、断线重连及多客户端干扰。
3. 使用真实 Qt 接收、解码、检测和绘制路径，分别统计每秒新源帧、新显示帧及最长无画面间隔。320×240、每秒至少20帧、最大150ms间隔应逐项验收；无法测得的光学端到端延迟明确留空。
4. 单路稳定后再进行三台相机同 AP 并发；以每路指标验收，不能只统计三路总吞吐量。
5. 明确 STM32/Luckfox 的最终分工，实现并验证完整命令、超时和回传链路，再做云台实物闭环和位移标定。

“零掉帧”“完全稳定”“从数学上杜绝”应从阶段报告中删除，改为注明版本、工况、时长和测量结果的可复核陈述。
