# 三台 ESP32-CAM 烧录与手机热点实测（2026-11-12）

已完成三块板的识别、原固件备份、独立编号烧录和三路实机测试。三块均为 ESP32-D0WD-V3 rev3.1、4MB Flash、4MB PSRAM、OV3660（PID 0x3660），不是 S3。此前第二路 S3 的地址和测试不能作为现在这块普通 ESP32-CAM 的结果。

电脑和三块板连接手机热点 Redmi K70E，2.4GHz、信道 13；测试时电脑为 10.166.101.174。视频通过 Wi-Fi 传输，串口用于供电、日志和复位，不传输视频。

保留用户已认可的原生 640×480 和硬件 JPEG 质量 18。Arduino-ESP32 3.3.12、AI-Thinker 引脚、20MHz XCLK、最新帧覆盖。UDP 使用 VID1 / 5006 / 1400 字节载荷，发送节拍 45ms、分片间隔 3ms、有限发送重试、整帧预算 45ms。节拍是发送目标，不是每路稳定帧率证明。

最终对照版本为 vga-paced-tx-v5：仅将 v4 的 IP_TOS=0x88 改为标准优先级 0x00，另改启动版本标识；画质与发送节拍保持不变。每块板的应用写入均通过 esptool 校验，随后串口复位确认设备编号、v5 版本、摄像头初始化、TOS 设置和 DHCP 地址。v5/ 保存构建清单、源码快照和启动/烧录日志，v4 的对应文件保存在本目录根部。两版 BIN 及整片备份包含本机 Wi-Fi 配置，仅保存在本地，不提交 GitHub。

使用项目 host/run.cmd 启动三路程序；host/camera-runtime.ini 与部署目录的配置已同步。热点 DHCP 地址变化后需要更新配置，未验证跨热点重启后的自动地址恢复。

## 用户后续观察

长测结束后，正式三路程序保持运行。用户随后反馈“现在又可以”，提供的截图显示三路均为 640×480，HUD 分别为 21.0、21.8、20.3fps。保留当前固件和画质参数。

这证明该次观察时三路均恢复到约 20fps；截图没有提供连续逐秒统计，不能据此改写此前长测结果。结合好坏交替的表现，无线链路波动是合理怀疑，具体原因尚未定位。

独立 Python 接收器的 60 秒三路并发测量（v4，采集与显示范围不同，不能直接当 Qt 显示成绩）：原设置平均 8.63 / 7.15 / 2.75fps，最长完整帧间隔 3339 / 1711 / 17101ms；关闭 802.11n 的兼容性对照平均 2.97 / 1.53 / 0.52fps，未见改善，已恢复原协议设置。原始结果在 v4-sources-60s/ 和 v4-bg-sources-60s/。已逐帧核对设备 ID 为 1/2/3、640×480，未发现解码错误或错误分辨率。

串口中摄像头采集通常约 27.8fps，卡顿时网络发送出现 errno=12（ENOMEM）及退避。这支持继续排查发送队列、热点转发及无线竞争，而不能仅凭剩余 PSRAM 或某个平均帧率断言原因。没有证明单独更换同型号板卡即可消除共享热点下的卡顿；也未测量光学到屏幕的端到端延迟或位移精度。部分截图中镜头拍到灰白近景，未据此验收镜头对焦或成像细节。

## 备份、恢复与验证

本机 COM3 / COM5 / COM11 的 before-full-4MB.bin 各 4194304 字节；backup-manifest.json 保存 SHA256。首次标准并行读取及一次单独读取发生串口数据损坏，失败日志保留，未将其作为有效备份。最终 backup_serial.py 逐块读取、每次只允许一个数据块在途，并与设备返回的整片 MD5 比较后才保存，三块均校验通过。原始备份和失败日志保存在本地；GitHub 保留校验清单及有效烧录/启动记录。

初次 v4 烧录引导程序、分区表、boot_app0 和应用，四个区段逐一通过写入校验；v5 只更新 0x10000 应用分区，保留同轮分区布局。烧录日志、启动日志、设备映射、源码与构建清单均保留。secrets.h 未复制到本报告目录，未记录或打印 Wi-Fi 密码。

提交的六份烧录文本日志仅清理了行尾空格，原始字节副本留在本机 `D:\esp32\backup\20261112-github-original-logs`，未改动日志中的烧录地址、数据量、校验结果或设备标识。

验证记录：三个独立 ID 的固件均编译成功；14 项 Python 协议/接收测试通过；git diff --check 通过（仅有换行格式提示）。完整物理证据以本次 JSON、串口日志和截图为准。测试程序已自动退出并释放所占串口与接收连接，随后可启动正式三路程序。
