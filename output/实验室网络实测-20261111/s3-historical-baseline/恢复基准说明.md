# 用户确认的旧 S3 传图基准

后续纠正（接回 COM6 实物后）：本目录最初只按 `quality40/out` 路径定位 BIN，身份判断不充分。真实启动出现优化编码器日志，进一步核对发现该目录的 `build.options.json` 与生成的 `.ino.cpp` 指向后续 `yuv-bgn` 实验；保留 BIN 为1007312字节，而历史 `flash-quality40.log` 应用为983216字节。因此下文所列 BIN 不能作为879帧那次原固件的身份凭证。已按保留的RGB源码另建 `D:\esp32\build-out\s3-rgb-http-rebuilt-20261111`，其应用983216字节，但只称源码重建，不宣称与旧BIN逐字节一致。实测与纠正详情见上级目录后续S3恢复报告。原说明保留以呈现发现和纠正过程。

2026-11-11，用户明确确认此前通过实验室 WiFi 看到视频的是 ESP32-S3 + GC2145，而非当前普通 ESP32 + OV3660。此前能传图与当前失败涉及不同硬件及固件，不能据此认定同一设备突然退化，也不能将路由器/天线/距离当成已确认根因。

已定位保留的原构建：`D:\esp32\build-out\optimize-20261106\quality40\out`。应用 1007312 字节，SHA256 `767811705ADF2925A0E6592812CEF97B3A6819CE4004778EED54CE25DB268509`。esptool image-info 实读该 BIN 为 ESP32-S3、8MB、DIO/80MHz，ESP-IDF v5.5.5；它不是后续隔离 Arduino 2.0.17 的 YUV 优化构建。对应暂存源码为 QVGA、RGB565 软件 JPEG 质量40、HTTP MJPEG、发送超时250ms，WiFi STA 且关闭休眠。原本地 secrets.h 的 SSID 已核对为 DH4504，未输出或归档密码。

对应历史记录 `tmp/esp32-optimize-20261106/quality40-warm/result.json`：请求60秒，接收879张不同JPEG，878张落在请求窗口内，320×240、无解码错误、一次HTTP连接，逐秒最低6帧，最长无新图像347.63ms。此结果证明当时能够传图，不证明稳定20fps。后续同日正式Qt120秒仍有长冻结，不能仅挑选879帧的较好窗口作为整体稳定证据。

本轮只读 esptool 芯片识别确认：当前COM5是ESP32-D0WD-V3、MAC 7C:D5:44:33:39:9C；当前未检测到旧S3。没有向普通ESP32写入S3镜像。四个所需BIN的当前哈希和长度已记录在 baseline-manifest.json。

下一步：用户接回旧S3，先实读芯片和相机身份、读取当前固件/保留恢复备份，再按对应历史镜像及布局恢复，重新发现DHCP地址，以HTTP验证真实源图像和Qt绘制。S3 bootloader偏移为0x0，普通ESP32为0x1000，不能混用；烧录必须显式限制--chip esp32s3。旧镜像可先恢复“能传图”的对照基准，稳定20fps仍须后续独立优化与验收。
