# 摄像头与实验室联网共存复测

2026-11-11，承接上次实验室 STA 传图失败后的继续排查。目标仍为实验室网络中的稳定 320×240 视频，未改为相机热点交付。

## 本轮新增证据

同一块 COM5、同一实验室 `DH4504`、电脑 `192.168.110.163`、相机 `192.168.110.96`，采用最小网络诊断固件，按阶段启停摄像头。网关和外网仅发起只读 HTTP HEAD 请求。

第一组 `path-probe/result.json`：

| 阶段 | 网关 HTTP | example.com HTTP | PC UDP 应答（4 / 512 / 1400 字节，各发 5 次） |
| --- | --- | --- | --- |
| 摄像头未启动、15 dBm | 200，连接 25ms | 200，连接 207ms | 1 / 0 / 0 |
| 摄像头启动、15 dBm | TCP 2503ms 超时 | TCP 2502ms 超时 | 0 / 0 / 3 |
| 摄像头反初始化、15 dBm | 200，连接 74ms | 200，连接 177ms | 5 / 5 / 5 |

这组对照说明：实验室网络能够让这块 ESP32 访问网关和外网，也能让 1400 字节相机应答到达电脑。因此，不能将固定的终端隔离规则视为已证实根因。启动摄像头与联网恶化存在关联，但第一阶段和开启阶段的小包结果本身有波动，不能据此断言已经找到某个唯一硬件故障。

第二组 `clock-memory-probe/result.json`：

- 10 MHz + PSRAM：网关 TCP 建立后收不到 HTTP 响应，外网超时；三种长度 PC 应答均 0/5。
- 16 MHz + PSRAM：网关、外网均超时；三种长度应答为 1/0/0。
- 20 MHz + 内部 DRAM：初始化成功但网关、外网仍超时；三种长度应答均 0/5。
- 随后重新初始化 20 MHz + PSRAM 遇到 SCCB/I²C 硬件超时，初始化返回 -1；此阶段没有运行摄像头，不能计作有效的“20 MHz 开启相机”对照。此时网关、外网与三种 PC 应答又恢复。
- 最终关闭阶段三种 PC 应答均 5/5。

第三组 `clock-pause-probe/result.json`：

- 20 MHz 相机开启阶段：网关成功、外网超时，三种 PC 应答均 5/5，说明症状并非每次开启即立即完全中断。
- 暂停 LEDC 相机时钟返回 0：网关成功、外网超时，PC 应答 5/1/0，未获得稳定恢复。
- 恢复时钟返回 0：网关 TCP 后无 HTTP 响应、外网超时，PC 应答 1/0/0。
- 反初始化：网关成功、外网超时，PC 应答 5/5/5。

因此，未把暂停时钟作为正式视频修复，也未把时钟/内存任一参数宣称为解决方案。这些是小包与连接诊断，不是连续视频帧率验证。

## 已完成的软件工作

`esp32cam/network_probe/network_probe.ino` 增加只读网关/WAN 检测、诊断用时钟和内存选择、暂停/恢复时钟，并由当前接口动态计算广播地址。该程序仍是诊断固件，不能作为正式摄像机使用。

每组脚本均在 finally 中关闭串口并恢复正式应用；最后一次 `clock-pause-probe/restore-sta-flash.log` 显示写回正式实验室 STA 应用 1046080 字节，esptool `Hash of data verified`。应用仍为上次 `final-sta-build-info.json` 记录的 SHA256 `0F1C8A1D6A8D549D18A7123C8D54D3B3266EC739C284461C10C0F7A4755272A3`。电脑仍连接 Private 类型实验室 `DH4504`，没有遗留相机热点连接或诊断进程。

诊断固件编译通过，相关源码 `git diff --check` 通过。没有声称正式实验室视频通过；上一轮最终 Qt 35 秒 0 帧的结果没有被这些小包测试覆盖。

## 当前判断与下一步

优先排查相机运行时的无线共存、安装位置、天线与供电条件；具体故障部件尚未确定。路由器管理权限可能对后续信道对照有帮助，但已不是唯一的下一步。

下一项低成本实物对照：在保持实验室 WiFi 不变的条件下，将相机放到实验室路由器约 1～2 米处，让板载天线区域远离电脑金属外壳、USB 集线器和遮挡，再重复正式视频验收。位置调整需要用户实际操作，工具不能完成。若仍失败，再做独立可靠 5V 供电/已确认天线连接方式的对照；目前不据此要求购买器件，不建议直接贴金属箔或盲目改焊天线选择电阻。

## GitHub 线索的适用范围

已读取乐鑫官方仓库的原始 issue 与评论并归档到 `camera-coexistence-issues.json`。这些是他人的故障报告，不是本机实验结果。

- [esp32-camera #662](https://github.com/espressif/esp32-camera/issues/662)：报告相机开启后联网恶化，后续评论涉及 ESP32/ESP32-S3 的时钟与天线干扰线索。仅作为本轮诊断方向。
- [arduino-esp32 #4655](https://github.com/espressif/arduino-esp32/issues/4655)：包含普通 ESP32-CAM 性能与天线讨论；多种互不一致的建议不能替代实测。
- [esp32-camera #869](https://github.com/espressif/esp32-camera/issues/869)：针对 S3 的 XCLK 反初始化问题；当前普通 ESP32 不能直接套用其 S3 寄存器修改。
- [官方 XCLK 实现](https://github.com/espressif/esp32-camera/blob/master/target/xclk.c)：核查普通 ESP32 使用 LEDC_LOW_SPEED_MODE 后才进行本地暂停时钟对照；源码快照归档在 `official-xclk.c`。
