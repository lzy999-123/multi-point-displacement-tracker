# S3 接回、备份、恢复与实验室传图复测

日期：2026-11-11。用户确认此前能够通过实验室 WiFi 传图的是 ESP32-S3 + GC2145，并将该板接回。当前结论：**已恢复通过实验室网络向 Qt 显示真实 320×240 视频，完整时段的稳定20fps / 最大间隔150ms验收仍未通过。**

## 实物识别与备份

最初新增 COM3 仅有 CH340，无串口数据；用户重新插拔后出现 COM6。esptool 实读 COM6 为 ESP32-S3 QFN56 rev0.2、8MB PSRAM、8MB Flash，MAC `E0:72:A1:D0:3D:E4`，与旧 S3 相符。COM5 则仍为普通 ESP32-D0WD-V3 / OV3660，两块板不能混用固件。

改写前读取8388608字节并在同一下载会话核对整片摘要：

- 备份：`D:\esp32\backup\20261111-162807-s3-e072a1d03de4-before-restore-8MB.bin`。
- SHA256：`5FAAF707B032D956B92AF747128F61FA63A95CAF7BFFD0F2BBAEBF9096FABF97`。
- 记录：`s3-historical-baseline/restore-*.json`，按文件中的COM6及备份路径核对。日志中 `Verification successful (digest matched)` 是本次备份校验证据。

整片备份可能包含原板网络配置，保存在仓库外，不将其当作可公开文件。之后只在已确认的 S3 上写入并校验应用/相应启动分区，没有向普通 ESP32 写入 S3 镜像。

## 旧版本身份的纠正

最初按 `optimize-20261106/quality40/out` 找到的应用是1007312字节。恢复后串口出现优化JPEG日志；核查该目录 `build.options.json`、生成的 `.ino.cpp` 后，发现它曾被后续 `yuv-bgn` 试验复用。历史 `flash-quality40.log` 的应用是983216字节。因此不能将目录中的现存BIN认定为历史879帧那次原版。

该判断失误已经纠正：旧说明增加纠正段落，baseline-manifest 标注 `historical_binary_identity_verified=false`，临时旧恢复脚本增加阻止再次误用的检查。历史879帧记录本身仍然有效，但它不能认证后来被覆盖的BIN。它也不代表稳定20fps通过。

随后从保留的原始 RGB565 / frame2jpg / JPEG质量40 / HTTP源码独立重建，应用983216字节，与旧记录大小一致；**只称源码重建，不能仅靠大小声称逐字节恢复原BIN**。对应 `s3-rgb-rebuilt/build-info.json` 保存实际源码和应用哈希。

## 当前 S3 固件

当前板上保留隔离构建的 S3 HTTP 快速编码版本：

- 工具链：Arduino-ESP32 3.3.12，`esp32:esp32:esp32s3:PSRAM=opi,FlashSize=8M`。
- GC2145：320×240、YUV422、20MHz XCLK、双缓冲、最新帧覆盖；JPEG质量40。
- 复用本机乐鑫 `esp_new_jpeg` 编码库，输入/输出按16字节对齐；复用编码器和PSRAM工作缓冲，保留HTTP最新帧发送。
- HTTP头携带 `X-Frame-Seq`，用于实际源图像去重和完整时段验证；发送超时1秒。
- 保留原STA联网方式，WiFi关闭休眠，现有相机连接实验室 `DH4504`，电脑网络类别为Private。
- 可用 `?nodelay=0/1` 做 TCP_NODELAY 对照；当前选择 `?nodelay=0`。
- 诊断串口 `1/2/3` 临时选择8.5/15/19.5dBm，`h` 配置HT20，`s`输出实际参数。本轮最后保留19.5dBm，实际读回78（四分之一dBm单位）、带宽读回1（HT20）。重启仍取默认配置，未写入持久的额外调参状态。

当前构建的冻结副本：`D:\esp32\build-out\s3-http-fast-radio-observed-20261111`，包含已测试BIN及非秘密源码；实际哈希见 `s3-radio-http/build-info.json`。工作目录 `s3-http-fast-20261111` 属于试验构建目录，后续不应仅靠路径名称推断版本。该固件尚未提升为“稳定验收完成”的正式基准，普通ESP32源码未因S3试验被替换。

S3 当前地址 `192.168.110.59`，电脑 `192.168.110.163`；DHCP地址变化后应重新发现。两块板的相机编号目前同为1，跨板自动发现可能报告编号冲突；本轮视频验收使用明确的S3地址，不把普通板数据当成S3数据。

无线功率等短对照按时间顺序进行，环境和自动曝光可能变化；不能把全部差异归因于单一参数。板端快速编码采集约27～35fps、压缩约18～19ms，HTTP发送仍偶发百毫秒至秒级等待。板端采集帧率不是实际显示验收。

Windows自动启动测试期间，Native WLAN QueryInterface实际读回 `background_scan_enabled=false`、`media_streaming_mode=true`，记录在 `s3-neighbor-control/wlan-hints-during-test.json`。因此不能未加证据地将停顿归因为本程序没有启用流媒体提示。

暂停和恢复普通相机后，短时源帧都曾通过；长时暂停普通相机的Qt测试仍失败，所以没有证明普通相机干扰或共用USB供电就是唯一根因。已如实保留两次130秒完整结果，没有只挑33fps区间报成功。

## 自动启动配置修复与当前使用

本机 `host/camera-runtime.ini` 与 `host/build/run/camera-runtime.ini` 已同步：通道1 `serialPort=COM6`，`wifiProfile`为空，URL `http://192.168.110.59:81/stream?nodelay=0`，保持电脑连接实验室DH4504。通道2保留旧COM3配置，当前不在线。原配置保存在各测量目录的 `previous-camera-runtime.ini`。

发现部署的旧版 live_viewer 自动模式读取EXE旁配置，最初还指向COM5/旧UDP地址。该试跑已关闭，日志另存 `s3-radio-http/aborted-old-runtime-config.serial.log`，没有验收结果，也不计入上述130秒测量。同步两处配置后，正确报告URL及串口日志均确认测试的是S3。

测试退出后已经启动 `host/build/run/DisplacementTracker.exe`，正常程序使用当前S3 HTTP地址，用户也可双击 `host/run.cmd`。同一相机同一时刻只保留一个视频客户端；后续复测前应正常关闭正式窗口。
